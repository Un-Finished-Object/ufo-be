# 채팅 성공 이벤트 저장과 재처리

[#149](https://github.com/Un-Finished-Object/ufo-be/issues/149)에 따라 `MESSAGE_CREATED`, `READ_UPDATED`를
DB에 저장해 전송 실패나 서버 재시작 후에도 재처리한다. 오류 이벤트는 즉시 전송한다.

## 저장과 재처리

- 이벤트 스냅샷과 전송 상태를 `chat_event_outbox`에 업무 데이터와 같은 트랜잭션으로 저장한다. 롤백하면 함께 취소한다.
- 데이터 변경 전에 사용자 행, 채팅방 행 순서로 DB 락을 건다. 전송할 때도 채팅방 행에 락을 걸어 같은 방의 이벤트가 동시에 전송되지 않게 한다.
- 커밋 후 콜백에서는 전송 작업을 전용 스레드 풀에 맡기고 바로 반환한다. 전송 작업은 별도 트랜잭션에서 미전송 이벤트를 ID 순으로 최대 50개 처리한다.
  앞선 이벤트의 전송이 실패하거나 재시도를 기다리고 있으면 같은 방의 다음 이벤트도 전송하지 않는다.
- 메시지를 삭제할 때도 같은 채팅방 행에 DB 락을 건다. 전송 직전에 삭제 여부를 확인하고, 삭제됐다면 식별 정보는 그대로 두고 본문만 빈 문자열로 보낸다.
- 전송 시도 횟수와 다음 재시도 시각, 성공 시각을 기록한다. 실패 시 재시도 간격을 30초부터 최대 5분까지 늘린다.
  전송 대기 큐가 가득 차 작업을 등록하지 못해도 이벤트는 DB에 남는다. 스케줄러는 기본 1초 간격으로 미전송 이벤트를 조회한다.

## 전송 보장 범위

- 전송 후 상태 커밋 전에 장애가 나면 해당 묶음의 이벤트가 중복 전송될 수 있다.
  수신 측은 `messageId`, `clientMessageId`, 사용자별 `lastReadMessageId`로 중복을 걸러내고 읽음 상태가 이전으로 돌아가지 않게 해야 한다.
- 전송 성공은 Spring 메시징 채널이 이벤트를 받아들였다는 의미다. 구독자가 실제로 받았는지, 오프라인 상태에서 놓친 이벤트를 복구할 수 있는지는 보장하지 않는다.
  채널이 이벤트를 받은 뒤 구독자에게 전달하기 전에 서버가 종료되면, 누락 여부를 확인할 수 없어 자동으로 재전송하지 못한다.
- Simple Broker의 서버 간 이벤트 전달은 별도 이슈 #148에서 다룬다.

## DB와 운영

Flyway V5로 테이블과 인덱스를 추가하며, 기존 메시지의 전송 기록은 소급 생성하지 않는다.
성공 기록은 7일 보관 후 기본 1시간 간격으로 정리하고, 미처리 기록은 자동 삭제하지 않는다.
대기 여부는 `published_at IS NULL`, 재시도 상태는 `attempts`와 `next_attempt_at`으로 확인한다.
이벤트 본문과 예외 메시지는 오류 로그에 넣지 않는다.
적용과 복구 절차는 [스키마 마이그레이션 안내](../database/schema-migrations.md)를 따른다.
