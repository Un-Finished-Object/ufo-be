# 배포 실패 시 이전 버전 복구 설계

## 배경

기존 배포는 새 컨테이너의 readiness 확인에 실패하면 종료했다. 이전 버전으로 돌아가는 절차가 없어 서비스 중단이 계속될 수 있었다. [#137](https://github.com/Un-Finished-Object/ufo-be/issues/137)에서는 이전 컨테이너를 보관하고 배포 실패 시 다시 실행하도록 바꾼다.

## 컨테이너 교체

기존 컨테이너의 이미지 ID와 실행 설정을 저장한 뒤, 컨테이너를 중지하고 이름을 바꿔 보관한다. 새 컨테이너는 Compose 서비스에 정의된 환경 변수, 포트, 볼륨과 네트워크 설정으로 실행한다.

내려받을 이미지는 커밋 태그로 지정하고, 다운로드가 끝나면 이미지 ID를 `image.yaml`에 기록해 Compose 설정에 추가한다. 새 컨테이너도 같은 이미지 ID를 사용하는지 확인한다.

`compose up`은 이름을 바꾼 컨테이너도 서비스 라벨로 찾아 교체할 수 있다. 복구할 컨테이너를 남기기 위해 새 버전은 `compose run --no-deps --service-ports --use-aliases`로 실행한다. 실행 중인 백엔드 이름은 `ufo-backend`로 유지한다.

`compose run`은 서비스에 지정한 재시작 정책을 초기화하므로 새 컨테이너에는 `unless-stopped`를 따로 설정하고 확인한다. 보관할 컨테이너는 원래 정책과 재시도 횟수를 기록한 뒤 자동 재시작을 끈다. 복구할 때는 기록한 정책부터 되돌린다.

새 컨테이너 생성이나 readiness 확인에 실패하면 실패한 컨테이너를 제거하고 원래 컨테이너를 다시 시작한다. 이때 현재 `.env`로 이전 버전을 재생성하지 않으므로 이전 환경 변수와 실행 설정이 유지된다. 복구한 서버도 readiness를 확인하며, 복구가 성공해도 배포 결과는 실패로 남긴다.

## 교체 전 확인

- 배포 잠금을 잡아 같은 서버에서 두 배포가 동시에 컨테이너를 바꾸지 못하게 한다.
- 새 이미지를 먼저 다운로드한다. 다운로드 실패 시 실행 중인 컨테이너를 중단하지 않는다.
- 이전 서버의 실행 상태와 readiness를 확인한다. 이미 준비되지 않은 서버를 정상 복구 버전으로 기록하지 않는다.
- 관리 포트는 호스트 `127.0.0.1`에만 연결돼야 한다. 외부 바인딩이나 포트 조회 실패는 배포 실패로 처리한다.
- 컨테이너 ID, 이미지 ID와 실행 설정은 `.deploy/`에 보관한다. 환경 변수가 포함된 파일은 소유자만 읽도록 하고 Actions 로그에 출력하지 않는다.

## 실패 처리

실패한 새 컨테이너는 삭제 전에 타임스탬프가 포함된 최근 200줄의 애플리케이션 로그를 저장한다. readiness는 확인 시각, 배포 또는 복구 단계, 컨테이너 ID, 시도 횟수, HTTP 상태와 curl 종료 코드를 기록한다. 연결 오류도 같은 기록에 남긴다. 로그 수집에 실패해도 이전 버전 복구는 계속한다. 로그 원문은 서버의 비공개 배포 기록에만 둔다.

| 실패 시점 | 처리 |
| --- | --- |
| 이미지 다운로드, 기존 상태 확인, 복구 자료 저장 | 기존 서버를 유지하고 종료 |
| 기존 서버 중지 또는 이름 변경 | 원래 컨테이너를 다시 시작하고 준비 상태 확인 |
| 새 컨테이너 생성 또는 readiness 확인 | 실패한 컨테이너 제거 후 이전 버전 복구 |
| 이전 버전이 없는 최초 배포 | 실패한 컨테이너를 제거하고 복구할 버전이 없음을 기록 |
| 이전 컨테이너 재시작 또는 readiness 확인 | 롤백 실패와 수동 복구 자료 위치 기록 |
| 배포 성공 후 이미지 정리 | 경고를 남기고 새 버전 유지 |

## 변경 범위

- `.github/workflows/deploy.yml`: 이미지 빌드와 업로드, SSH 접속, 배포 스크립트 실행.
- `scripts/deployment/deploy-backend.sh`: 교체 전 상태와 이미지 보관, 실패 시 복구, 복구 결과 확인.
- `.gitignore`: 비밀 환경 변수가 들어 있는 `.deploy/` 제외.
- `DeploymentReadinessTest`: 실제 배포 스크립트를 실행해 성공과 실패 후 컨테이너 상태 검증.
- [배포와 롤백 절차](../deployment/rollback.md): 서버 준비, 결과 확인, 수동 복구와 보관 자료 정리.

## 검증

테스트는 워크플로의 `script_path`가 가리키는 배포 스크립트를 읽어 실행한다. Docker와 HTTP 호출은 대역으로 바꿔 운영 서버나 DB에 연결하지 않는다. 기존 서버가 유지되는지, 같은 컨테이너 ID로 복구되는지, 복구 후에도 배포가 실패로 끝나는지 확인한다. 새 서버의 readiness 지연, 리다이렉트, 외부 관리 포트, 다운로드 실패, 교체 도중 실패, 최초 배포 실패와 롤백 실패를 각각 다룬다.

실패한 컨테이너를 제거한 뒤에도 애플리케이션 로그와 readiness 진단 기록이 남는지 확인한다. 로그 수집 실패가 복구를 막지 않는지, 로그 원문이 실행 결과에 노출되지 않는지도 검증한다.

대상 테스트는 `.\gradlew.bat test --tests '*DeploymentReadinessTest' --no-daemon`으로 실행한다. 대상 테스트를 통과하면 `.\gradlew.bat test --no-daemon`으로 기본 테스트 전체를 확인한다.

## 운영상 한계

기존 서버를 중지한 뒤 새 서버를 실행하므로 교체 중 요청을 처리하지 못하는 시간이 생긴다. 종료 신호에는 복구를 시도하지만 강제 종료, 호스트 장애나 Docker 데몬 장애에는 자동 복구를 보장할 수 없다.

배포는 DB 컨테이너를 교체하거나 마이그레이션을 실행하지 않는다. 컨테이너를 보관해도 공유 볼륨과 DB 데이터는 과거 시점으로 돌아가지 않는다. DB 변경은 이전 애플리케이션과 호환돼야 하며, 스키마 변경과 복구 기준은 [#136](https://github.com/Un-Finished-Object/ufo-be/issues/136)에서 다룬다.
